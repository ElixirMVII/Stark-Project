# DECISIONS — จุดที่ทำต่างจาก spec หรือ spec ไม่ได้ระบุ

จดเรียงตามเวลา แต่ละข้อบอกว่า spec ว่าอย่างไร เจออะไร และตัดสินใจอย่างไร

## M0

### D1 · root ของ repo คือโฟลเดอร์ `aether/` ใน spec
spec วาดโครงสร้างไว้ใต้ `aether/` ส่วน repo นี้ใช้ root ของ repo เป็นโฟลเดอร์นั้นเลย
(`pyproject.toml`, `config.toml`, `src/aether/` อยู่ที่ root) ไม่ซ้อนโฟลเดอร์อีกชั้น

### D2 · mediapipe 1.2.x (ไม่ใช่ 0.10.x)
- เวอร์ชันล่าสุดบน PyPI ตอนทำคือ **mediapipe 1.2.3** (wheel `py3-none-win_amd64`)
  จึงกำหนด `mediapipe~=1.2` ใน `pyproject.toml`
- ตรวจจาก package ที่ติดตั้งจริง: ไม่มี `solutions` แล้ว, `mediapipe.tasks.python.vision` มี
  `GestureRecognizer`, `RunningMode.VIDEO`, `recognize_for_video(image, timestamp_ms)` และ
  `HandLandmarksConnections.HAND_CONNECTIONS` ตามที่ spec คาดไว้
- `recognize_for_video` โยน `ValueError` ถ้า timestamp ไม่เพิ่ม → `HandTracker.process`
  บังคับให้เพิ่มอย่างน้อย +1ms เสมอ
- มี test กันไม่ให้ `mp.solutions` / `mediapipe.solutions` โผล่ในโค้ด (`tests/test_tracker.py`)

### D3 · OpenCV มาจาก mediapipe
`pip install mediapipe` ดึง **`opencv-contrib-python`** (5.0.0.93) มาเอง จึงไม่ใส่ OpenCV ใน
dependency ของเรา และ **ห้ามลง `opencv-python` เพิ่ม** (ทั้งคู่ให้ module `cv2` จะชนกัน)

### D4 · Handedness: ต้องสลับ label เมื่อ flip ภาพ (ต่างจาก spec)
- **spec ว่า:** MediaPipe ถือว่าภาพเป็นแบบกระจก พอ flip แนวนอนแล้ว label ซ้าย/ขวาจะตรงกับมือจริง
- **ที่เจอ (mediapipe 1.2.3 + `gesture_recognizer.task`):** กลับกัน — ภาพที่ **ไม่ flip** ให้ label
  ตรงกับมือจริง ส่วนภาพที่ flip แล้ว label จะสลับข้าง ทดสอบกับภาพตัวอย่างของ MediaPipe 3 ภาพ
  (`pointing_up.jpg` มือซ้ายจริง → `Left`, `victory.jpg` และ `thumbs_down.jpg` มือขวาจริง →
  `Right`; พอ flip ทั้งสามภาพให้ label ตรงข้าม)
- **ตัดสินใจ:** ยัง flip ภาพก่อนส่งเข้าโมเดลตาม spec (ให้ทิศการขยับเหมือนส่องกระจก) แล้วสลับ
  label ใน `tracker.user_handedness()` เมื่อ `camera.mirror = true` ถ้าปิด mirror จะใช้ label ตรงๆ
- **ต้องยืนยันกับกล้องจริง** ในขั้นทดสอบ M0 (ยกมือขวา → ต้องขึ้น `RIGHT`)

### D5 · ไฟล์ `.task` ไม่ได้ขึ้นต้นด้วย `PK`
ไฟล์โมเดลเป็น zip ที่มี byte `00 00` นำหน้า signature การตรวจไฟล์ใน `download_assets.py`
จึงใช้ `zipfile.is_zipfile()` แทนการเทียบ byte แรก

### D6 · ชุดเสียง Kenney ต้องโหลดเองผ่านเบราว์เซอร์
- **spec ว่า:** ให้ `download_assets.py` โหลดทุกไฟล์ ถ้าโหลดอัตโนมัติไม่ได้ให้บอกวิธีโหลดเอง
- **ที่เจอ:** หน้า asset ของ kenney.nl ไม่มีลิงก์ `.zip` ตรงแล้ว ปุ่ม Download เปิดหน้าต่างบริจาค
  แล้วใช้ JavaScript ขอ "signed link" แบบใช้ครั้งเดียว และเว็บตอบ 403 กับ client อัตโนมัติบางตัว
- **ตัดสินใจ:** ไม่เขียนสคริปต์เลี่ยงขั้นตอนของเว็บ สคริปต์จะตรวจว่ามี zip ใน `assets/_downloads/`
  หรือยัง (ยอมรับชื่อไฟล์ที่เบราว์เซอร์ตั้งให้ เช่นมี ` (1)` ต่อท้าย) ถ้ายังไม่มีจะบอกลิงก์และที่วาง
- ตารางเลือกเสียงใน `convert_sounds.py` (`ROLES`) — **ชื่อไฟล์ยืนยันแล้ว** (M4+) จากรายชื่อไฟล์ของชุด
  Interface Sounds ในโปรเจกต์สาธารณะที่ใช้ชุดเสียงนี้ (CC0): `click_001–005`, `drop_001–004`,
  `confirmation_001–004`, `close_001–004`, `scroll_001–005`, `minimize_001–009`, `error_001–008` มีอยู่จริง
  และ `computerNoise_000` อยู่ในชุด Sci-Fi Sounds ไฟล์ที่ตารางเลือกจึงตรงกับของจริงทุกตัว
  **ยังไม่ได้ฟัง** ว่าเสียงเข้ากันหรือไม่ — เลือกใหม่ได้ด้วย `--list` และ `--map ROLE=FILE`

### D7 · ส่งโมเดลเข้า MediaPipe เป็น bytes
`HandTracker` อ่านไฟล์โมเดลด้วย Python แล้วส่งเป็น `model_asset_buffer` แทน `model_asset_path`
เป็นการกันไว้ก่อนสำหรับ path ที่มีอักษรไทย (เช่นชื่อ user ของ Windows) ซึ่งฝั่ง C อาจเปิดไม่ได้
(ยังไม่ได้ทดสอบว่า path แบบนั้นพังจริงหรือไม่)

### D8 · UI หยิบเฟรมล่าสุดเอง ไม่รับทุกเฟรมผ่าน signal queue
worker thread (กล้อง → tracker) เก็บ `FramePacket` ล่าสุดไว้ แล้วส่ง signal `frame_ready`
เฉพาะเมื่อ UI หยิบอันก่อนไปแล้ว ถ้า UI วาดไม่ทัน เฟรมเก่าจะถูกทิ้งแทนที่จะสะสมในคิวจนภาพหน่วง
(ฝั่งส่ง input ให้ OS ใน M1 จะทำใน worker thread ตาม spec จึงไม่ได้รับผลจากความเร็วของ UI)

### D9 · key ที่ไม่รู้จักใน `config.toml` เป็น error
spec ให้ validate config แต่ไม่ได้ระบุกรณี key แปลกปลอม เลือกให้ **error พร้อมบอก key ที่ใช้ได้**
แทนการข้ามเงียบๆ เพราะค่าพวก threshold มีผลต่อความปลอดภัยของการคุมเมาส์ พิมพ์ผิดแล้วไม่รู้ตัวจะอันตราย

### D10 · สิ่งที่เลื่อนไป milestone ถัดไป
- `tools/record_landmarks.py` — ทำใน M1 (ใช้อัด fixture สำหรับ test gesture)
- `Orbitron.ttf` ที่โหลดมาเป็น variable font ไฟล์เดียว (`Orbitron[wght].ttf` ใน repo google/fonts)
  การเลือกน้ำหนักฟอนต์ใน Qt จะจัดการตอนทำ HUD (M2)

## M1

### D11 · Global hotkey ใช้ `RegisterHotKey` (Win32) แทน pynput
- **spec ว่า:** ใช้ pynput ทำ global hotkey
- **ที่เจอ (อ่านจาก source ของ pynput 1.8.2):** `GlobalHotKeys` บน Windows เทียบ hotkey จาก
  *ตัวอักษร* ที่ปุ่มนั้นพิมพ์ออกมาใน layout ปัจจุบัน (`Listener.canonical` → `char_from_scan`)
  ถ้าเปิดแป้นไทยอยู่ ปุ่ม G จะให้ "เ" → `<ctrl>+<alt>+g` ไม่ติด ซึ่งรับไม่ได้สำหรับปุ่มหยุดฉุกเฉิน
- **ตัดสินใจ:** บน Windows ใช้ `RegisterHotKey` ผ่าน ctypes (spec อนุญาต ctypes/Win32) ใน thread
  ของตัวเองพร้อม message loop — เทียบจาก virtual-key code จึงไม่ขึ้นกับภาษาของแป้น และไม่ต้องใช้
  keyboard hook รูปแบบใน config ยังเป็น `<ctrl>+<alt>+g` ตาม spec (parse เองใน `hotkeys.py`)
  นอก Windows (เครื่อง dev) ถอยไปใช้ pynput
- **ยังไม่ได้ยืนยันบน Windows จริง** — ส่วน loop/การลงทะเบียน test ด้วย API ปลอม แต่ signature ของ
  ctypes ต้องลองบนเครื่องจริง (อยู่ใน checklist M1)
- pynput ยังใช้สำหรับเมาส์ตาม spec (`SetCursorPos` + `SendInput`)

### D12 · โมดูลที่เพิ่มจากโครงสร้างใน spec
- `pipeline.py` — ร้อย tracker → engine → executor ภายใต้ lock เดียว ไม่ขึ้นกับ Qt (test ง่าย)
  สถานะ ARM มีแหล่งความจริงเดียวคือ engine; hotkey/watchdog/worker เรียกผ่าน lock เดียวกัน
- `hotkeys.py` — ดู D11
- `recording.py` — อ่าน/เขียน JSONL ของ landmark และเล่นซ้ำเข้า engine (ใช้ทั้ง tool และ test)

### D13 · รายละเอียดของ gesture engine ที่ spec ไม่ได้ระบุ
- **คลิกเกิดตอนปล่อยนิ้ว** (ต้องรอดูว่าจะกลายเป็นการลากหรือไม่) ส่วน **คลิกขวาเกิดทันที** ที่จีบ
  โป้ง+กลางครบ 40ms (ไม่มีการลากด้วยปุ่มขวา)
- **ดับเบิลคลิก:** จีบครั้งที่สองภายในเวลาดับเบิลคลิกของ OS (`GetDoubleClickTime`) และห่างจากจุดแรก
  ไม่เกิน ~32px จะถูกส่งเป็นคลิกที่ **ตำแหน่งเดิมของคลิกแรก** เพื่อให้ OS นับเป็นดับเบิลคลิกแน่นอน
  แม้มือจะขยับเล็กน้อย
- **การจีบที่เห็นแค่เฟรมเดียว (< 40ms) ไม่นับ** — กัน landmark เพี้ยนชั่วเฟรม
- **ระหว่างลาก ต้องเห็นนิ้วห่างต่อเนื่อง 30ms จึงปล่อย** — กันของหลุดมือเพราะ landmark เพี้ยนเฟรมเดียว
- **ต้องเห็นนิ้วห่างเกิน `pinch.off` หนึ่งครั้งก่อนจีบได้** หลัง arm หรือหลังมือเพิ่งเข้าเฟรม —
  กันคลิก/ลากเองถ้ามือเข้ามาในท่านิ้วชิดกันอยู่แล้ว
- **กำมือ ≠ จีบ:** ถ้าปลายนิ้วพับกลับมาใกล้ข้อมือกว่าโคนนิ้ว (`geometry.finger_curled`, ใช้ world
  landmark 3D) จะไม่นับเป็นการจีบ และการจีบที่กำลังรออยู่จะถูกยกเลิก ค่า `CURL_RATIO = 0.8`
  ตั้งจากสัดส่วนมือโดยประมาณ **ยังไม่ได้ปรับกับข้อมูลจริง**
- **โป้งชิดทั้งนิ้วชี้และนิ้วกลาง:** นิ้วที่ชิดกว่าชนะ
- **Pinch-lock แบบไม่กระโดด:** `mapping.PointerTracker` สะสมระยะที่เคอร์เซอร์ตามหลังเป้าตอน gain
  ต่ำ แล้วค่อยๆ เก็บคืนตามที่มือขยับ (50% ของระยะขยับต่อเฟรม) แทนการกระโดดกลับไปหาเป้า
- **มือหายช่วงสั้น (< 300ms) คงสถานะเดิม** ไม่ปล่อยปุ่ม ไม่คลิกซ้ำ; ครบ 300ms จึงปล่อยและกลับ IDLE
- **เลือกมือ:** ถ้าเจอมือข้างถนัดสองมือในเฟรมเดียว เลือกมือที่อยู่ใกล้ตำแหน่งเดิม
- **Majority vote:** เฟรมที่ยังไม่เห็น (เพิ่งเริ่ม/reset) นับเป็น `None` ท่าใหม่ต้องเห็นเกินครึ่ง window เสมอ

### D14 · สกรอล
- สกรอลตาม **ระยะที่มือขยับ** (เหมือนลากหน้ากระดาษ) โดย `scroll.deadzone` เป็น "ระยะฟรี" ที่มือขยับ
  ได้ก่อนเริ่มสกรอล (กันมือสั่น) ไม่ใช่ deadzone ต่อเฟรม
- มือขึ้น = เลื่อนขึ้น (เหมือนหมุนล้อเมาส์ขึ้น) เพิ่ม key `scroll.invert` (ไม่มีใน spec) ไว้กลับทิศ
- ล็อกแกนเดียวระหว่างสกรอล หยุด 300ms จึงเลือกแกนใหม่
- ส่งเป็น **notch เต็ม** ของล้อเมาส์ (สะสมเศษไว้) ไม่ส่ง delta ย่อย เพราะบางโปรแกรมไม่รองรับ
  high-resolution wheel; `SCROLL_NOTCHES_PER_UNIT = 30` (ขยับมือเต็มความสูงเฟรม = 30 notch)

### D15 · Watchdog ปล่อยปุ่มเมื่อกล้องค้าง
spec ให้ปล่อยปุ่มถ้ามือหายเกิน 300ms แต่ถ้ากล้องค้าง worker thread จะไม่ได้เฟรมมาตัดสินเลย
จึงมี timer ใน UI thread เรียก `Pipeline.check_stall()` ทุก 100ms: ไม่มีเฟรมเกิน 300ms → engine
ทำเหมือนมือหาย (ปล่อยปุ่ม กลับ IDLE)

### D16 · Fixture ใน `tests/fixtures/` เป็นข้อมูลสังเคราะห์ (ตอนนี้)
ยังไม่มีกล้องให้อัดจริง ไฟล์ `synthetic_*.jsonl` จึงสร้างจากมือจำลอง (`tests/handsim.py` ผ่าน
`tests/make_synthetic_fixtures.py`) ใช้ทดสอบเส้นทาง อัด → อ่าน → เล่นซ้ำ ไฟล์ที่อัดจากกล้องจริงด้วย
`tools/record_landmarks.py --expect ...` วางในโฟลเดอร์เดียวกันแล้ว `pytest` จะตรวจให้อัตโนมัติ
**มือจำลองไม่มี noise/มุมมือแบบของจริง** ค่า threshold ทั้งหมดจึงต้องยืนยันกับกล้องจริงอีกครั้ง

### D17 · ย้ายเคอร์เซอร์ด้วย `SetCursorPos` (ผ่าน pynput)
pynput บน Windows ย้ายเคอร์เซอร์ด้วย `SetCursorPos` และกดปุ่ม/ล้อด้วย `SendInput` ซึ่งเป็นแบบเดียวกับ
ที่ pyautogui ใช้ ถ้าทดสอบจริงแล้วการลากใช้ไม่ได้กับบางโปรแกรม ทางแก้คือเปลี่ยน `PynputBackend.move`
ไปใช้ `SendInput` แบบ absolute (แก้จุดเดียวใน `actions.py`)

## M2

### D18 · Reticle ใช้ตำแหน่งจาก engine ไม่ได้อ่านตำแหน่งเมาส์จริง
spec ว่า reticle "ตามเคอร์เซอร์" — ใช้ `EngineSnapshot.cursor` (ตำแหน่งที่ engine สั่งย้าย) ตรงๆ
ทุกเฟรมของกล้อง ไม่ผ่านการ smooth เพิ่ม จึงตรงกับเคอร์เซอร์จริงพอดีและไม่มี lag เพิ่ม ผลพลอยได้:
- `DISARMED` / `--dry-run`: reticle แสดงตำแหน่งที่เคอร์เซอร์ *จะ* อยู่ โดยไม่ขยับเมาส์จริง
- ไม่เห็นมือข้างถนัด → reticle จางหาย (ถ้าผู้ใช้ขยับเมาส์จริงเอง reticle ไม่ตาม)

### D19 · Overlay เตี้ยกว่าจอ 1px
หน้าต่างบนสุดที่คลุมจอพอดีอาจถูก Windows มองเป็นแอป fullscreen (กระทบ taskbar/การแจ้งเตือน)
จึงตั้ง geometry ให้เตี้ยกว่าจอ 1 logical px เป็นการกันไว้ก่อน **ยังไม่ได้ยืนยันบน Windows จริง**
ว่าจำเป็นหรือไม่

### D20 · ต้นทุนการวาด: cache ชั้นที่ไม่เปลี่ยน และ glow สองชั้น
- spec ให้ glow ด้วยเส้นหนาโปร่งแสง 2–3 ชั้น — ใช้ **2 ชั้น** เพราะเส้นหนาโปร่งแสงคือส่วนที่แพงที่สุด
  ชั้นที่สามแทบมองไม่เห็นแต่กินเวลาเพิ่มราว 40%
- กรอบแผง (พื้น + ขอบเรืองแสง + เส้นสแกน) และส่วนที่ไม่ขยับของ reticle (ฉากหลัง วงนอก tick)
  วาดครั้งเดียวลง `QPixmap` ที่ความละเอียดจอจริง (`theme.LayerCache`, key รวม devicePixelRatio)
- วัดบนเครื่อง dev (Linux, software raster, ไม่ใช่เครื่องเป้าหมาย): ทั้ง HUD ที่ 60fps กิน
  ~13% ของหนึ่ง core ที่ scale 100% และ ~17% ที่ 150% (ก่อน optimize: 20% / 30%)
  ค่าจริงบน Windows ต้องวัดจาก Task Manager (อยู่ใน checklist M2)
- `update()` เฉพาะกรอบของชิ้นที่เปลี่ยน: reticle (กรอบเดิม ∪ กรอบใหม่), แผงเมื่อค่าที่แสดงเปลี่ยน,
  telemetry ทุก 500ms; ไม่มีมือและไม่มีแอนิเมชัน = ไม่วาดเลย (มี test ยืนยัน)

### D21 · รายละเอียด HUD ที่ spec ไม่ได้ระบุ
- Reticle มีฉากหลังเข้มโปร่งแสงวงกลม เพื่อให้เส้นสีฟ้าอ่านออกบนหน้าต่างสีขาว
- Hand radar ซูมที่มือข้างถนัดให้เต็มกรอบ (เห็นการจีบชัด) แทนการแสดงทั้งเฟรมกล้อง
- ป้ายสถานะมีบรรทัดเตือนสีแดง (`CAMERA LOST`, `PIPELINE ERROR`) + เสียง error
- เสียง: `click` ใช้ทั้งตอนคลิกและตอนเริ่มลาก, `release` ตอนจบการลาก; สกรอลไม่มีเสียง (ถี่เกินไป)
- ฟอนต์ Orbitron เป็น variable font: เลือกน้ำหนักด้วย `QFont.setVariableAxis("wght", ...)`
  ถ้าไม่มีไฟล์ฟอนต์จะใช้ฟอนต์ของระบบแทน (HUD ยังทำงานได้)
- ไม่มีไฟล์เสียง / ไม่มีอุปกรณ์เสียง: `SoundPlayer` เงียบโดยไม่ error (log บอกครั้งเดียวว่าขาดไฟล์ไหน)

### D22 · สิ่งที่ยืนยันไม่ได้บนเครื่อง dev (ต้องลองบน Windows)
- คลิกทะลุจริง (ตั้ง `WindowTransparentForInput` + `WA_TransparentForMouseEvents` แล้ว มี test
  ตรวจ flag แต่พฤติกรรมจริงขึ้นกับ Windows)
- HUD อยู่บนสุดเหนือหน้าต่างทั่วไป และไม่โผล่ใน taskbar
- การเล่นเสียงผ่าน `QSoundEffect` (เครื่อง dev ไม่มีอุปกรณ์เสียง)

## M3

### D23 · การปัดต้องเริ่มจากมือที่แบนิ่ง
- **spec ว่า:** อยู่ใน GESTURE แล้ว palm_center ขยับเกิน 25% ของความกว้างเฟรม (หรือ 20% ของความสูง)
  ภายใน 300ms และแกนหลัก ≥ 2 เท่าของแกนรอง
- **ปัญหาถ้าทำตามตรงๆ:** ยกมือที่แบอยู่เข้าเฟรมเร็วๆ ก็เข้าเงื่อนไข "ปัดขึ้น" และการดึงมือกลับหลังปัดก็เข้า
  เงื่อนไขปัดทิศตรงข้าม
- **ตัดสินใจ:** เพิ่มเงื่อนไขว่าต้องเห็นมือแบ **นิ่ง 150ms** ก่อน (กลางฝ่ามือขยับไม่เกิน 3%/4% ของเฟรม)
  การปัดจึงจะนับ และหลังปัดติดแต่ละครั้งต้องพ้น cooldown แล้วนิ่งใหม่อีกรอบ HUD แสดงเข็มทิศจาง/สว่าง
  ให้รู้ว่าพร้อมหรือยัง เงื่อนไขระยะ/เวลา/อัตราส่วนเป็นไปตาม spec (อัตราส่วน 2:1 วัดเป็น px)
- ระหว่างปัดเร็วๆ ภาพอาจเบลอจนโมเดลไม่เห็นเป็น `Open_Palm` ชั่วครู่ จึงผ่อนผันอยู่ในโหมดต่ออีก
  `swipe_window_ms` หลังท่าหายไป
- การจีบระหว่างโหมด GESTURE ออกจากโหมดทันที (ไม่รอผลโหวตท่า) เพื่อไม่ให้พลาดคลิกที่ทำต่อจากแบมือ

### D24 · ท่าพิเศษเริ่มได้เฉพาะใน active region
spec ไม่ได้ระบุ — 🖐 ✊ 🤟 จะเริ่มนับเมื่อจุดคุมเคอร์เซอร์ของมืออยู่ใน `pointer.active_region` (+ขอบเผื่อ 5%)
เท่านั้น เหตุผล: มือที่วางพักมักอยู่ขอบล่างของเฟรมในท่ากำหลวมๆ ถ้าไม่จำกัด ✊ ค้าง 0.6 วินาทีจะย่อหน้าต่างเอง
(การขยับเคอร์เซอร์/คลิก/สกรอลไม่ถูกจำกัดด้วยเงื่อนไขนี้)

### D25 · ท่าค้าง (✊, 🤟)
- เริ่มนับจากผลโหวตท่า (3 ใน 5 เฟรม) จึงใช้เวลาจริง ≈ ค่าใน config + ~100ms
- ติดแล้วต้อง **เลิกทำท่านั้น** และพ้น `cooldown_ms` ก่อนจะนับใหม่ — ค้างยาวๆ ไม่ยิงซ้ำ
  (spec ให้ cooldown 800–1500ms; ใช้ `gestures.cooldown_ms` ค่าเดียวกับการปัด + เงื่อนไขต้องเลิกท่า)
- 🤟 ทำงานทั้งตอน ARMED (→ disarm) และ DISARMED (→ arm) ตอน DISARMED เป็นท่าเดียวที่ engine รับ
- การสลับ ARM ไม่ล้างผลโหวตท่า มิฉะนั้นท่าที่ยังค้างอยู่จะสลับกลับเองทันที
- ✊ ใช้ป้าย `Closed_Fist` ของโมเดลอย่างเดียว (ไม่ผูกกับ `finger_curled`) เพื่อไม่ให้ท่านี้ขึ้นกับ
  heuristic ที่ยังไม่ได้ปรับกับข้อมูลจริง (ดู D13)

### D26 · ซูมสองมือ
- "จีบสองมือพร้อมกัน" = มือทั้งสองเริ่มจีบห่างกันไม่เกิน 400ms (`ZOOM_SYNC_MS`) — มืออีกข้างที่จีบค้าง
  มานานแล้ว (วางพัก) จะไม่ทำให้การคลิกปกติกลายเป็นซูม
- มือหลักจีบก่อนแล้วมืออีกข้างตามมาก่อนครบ `drag_hold_ms` → ยกเลิกการคลิก/ลาก เข้าโหมดซูม;
  ถ้าเริ่มลากไปแล้ว (เกิน 250ms) จะไม่เปลี่ยนเป็นซูม (ไม่อยากปล่อยของที่ลากอยู่กลางทาง)
- วัดระยะจากจุดคุมเคอร์เซอร์ของสองมือ (px) ทุกครั้งที่ระยะเปลี่ยน ×(1 + `zoom_step`) หรือ ÷ = 1 notch
  ของ `Ctrl`+ล้อเมาส์ (มี hysteresis ในตัว จึงไม่สั่นไปมาเมื่อมือไหวเล็กน้อย)
- จบเมื่อมือใดมือหนึ่งปล่อยนิ้ว หรือมืออีกข้างหายเกิน 300ms; มือหลักต้องปล่อยนิ้วก่อนจึงคลิกได้อีก

### D27 · การกดปุ่มลัดและการย่อหน้าต่าง
- `[actions]` รับปุ่มลัด (`ctrl+win+left`, `f11`, …), `minimize_foreground` หรือ `none` และถูก validate
  ตอนโหลด config
- ตัวอักษร/ตัวเลขในปุ่มลัดส่งเป็น **virtual-key code** ผ่าน pynput (`KeyCode.from_vk`) ไม่ใช่ตัวอักษร
  เพราะถ้าเปิดแป้นไทยอยู่ pynput จะส่ง "d" เป็น Unicode ซึ่ง Windows ไม่นับเป็น `Win+D`
  (อ่านจาก source ของ pynput — **ยังไม่ได้ยืนยันบน Windows จริง** อยู่ใน checklist M3)
- คีย์ที่กดเพื่อปุ่มลัด/ซูมถูกปล่อยเสมอแม้ backend จะพังกลางทาง และ `release_all()` ปล่อยคีย์ด้วย

  `Progman`, `WorkerW`, `Shell_TrayWnd` และ `Shell_SecondaryTrayWnd` (taskbar ของจอที่สอง — เพิ่มจาก spec)

## M4

### D29 · โหลด config ใหม่ = สร้างชุดทำงานใหม่ทั้งชุด
`AppController` (อยู่ตลอดอายุ process) เป็นเจ้าของ tray และ wizard ส่วน `AetherApp` คือหนึ่งชุดของ
กล้อง + tracker + engine + HUD + hotkey ตาม config หนึ่งชุด เมนู "โหลด config ใหม่" จะ:
อ่าน config ใหม่ → ถ้าผิด แจ้งเตือนและใช้ชุดเดิมต่อ → ถ้าถูก ปิดชุดเดิม (ปล่อยปุ่มเมาส์ก่อนเสมอ) แล้ว
สร้างชุดใหม่ซึ่ง **เริ่มแบบ DISARMED** (เหมือนเปิดแอปใหม่ ตามกติกา "เริ่มแบบ DISARMED เสมอ") และไม่เล่น
boot animation ซ้ำ เลือกวิธีนี้แทนการ patch ค่าทีละตัว เพราะค่าแทบทุกตัวกระจายอยู่หลายอ็อบเจกต์
(กล้อง, tracker, filter, HUD theme, hotkey) — สร้างใหม่ทั้งชุดได้ผลถูกต้องแน่นอน แลกกับเวลาโหลดโมเดล ~1 วินาที

### D30 · Calibration
- วัด pinch_ratio ตอนพักและตอนจีบ (ขั้นละ 2 วินาที) แล้วตั้ง `pinch.on` เหนือค่าตอนจีบ (เปอร์เซ็นไทล์ 90)
  ไม่เกิน 35% ของช่องว่างระหว่างสองท่า และ `pinch.off = 1.5 × on` (สัดส่วนเดียวกับค่าเริ่มต้น 0.25/0.38)
  แต่ไม่เกิน 70% ของช่องว่าง ถ้าสองท่าห่างกันไม่ถึง 0.12 ถือว่าวัดไม่ได้ ให้ทำใหม่
- active region = เปอร์เซ็นไทล์ 3–97 ของตำแหน่งมือตอนขยับให้ทั่ว หดขอบเข้า 5% ต้องกว้าง ≥ 25% และสูง ≥ 20%
  ของเฟรม
- `calibration.json` อยู่ข้าง `config.toml` และ **ทับ** 3 ค่านี้ตอนโหลด (ค่าอื่นยังมาจาก `config.toml`)
  เลือกเก็บแยกไฟล์ตาม spec แทนการเขียนทับ `config.toml` ของผู้ใช้ — ลบไฟล์ = กลับค่าเดิม,
  `--no-calibration` = ไม่ใช้ชั่วคราว
- ระหว่างเปิด wizard แอปบังคับ DISARMED (ถ้ามีการ arm จะถูกปิดทันที) เพราะผู้ใช้จะจีบนิ้วซ้ำๆ
- เวลาในแต่ละขั้นเดินเฉพาะตอนเห็นมือข้างถนัด และตัดช่วงเฟรมขาดที่นานเกิน 200ms ไม่ให้นับ
- ตัวเลขทั้งหมดตั้งจากเหตุผลเชิงสัดส่วนและทดสอบกับมือจำลอง **ยังไม่ได้ปรับกับผู้ใช้จริง**

### D31 · Path ของ build: ไฟล์ผู้ใช้ข้าง exe, asset ใน `_internal`
- PyInstaller 6 วางไลบรารีและ data ไว้ใน `_internal\` (`sys._MEIPASS`) — `bundle_root()` ชี้ที่นั่น
  (assets, config.toml ต้นฉบับ) ส่วน `app_root()` คือโฟลเดอร์ของ exe (config.toml ที่ผู้ใช้แก้,
  calibration.json, logs) ตอนรันจาก source ทั้งสองคือ root ของ repo
- spec คัดลอก `config.toml`, `README.md`, `LICENSES.md` ไปข้าง exe (ไม่ทับ config.toml ที่มีอยู่แล้ว)
  ถ้าผู้ใช้ลบ config.toml ข้าง exe จะใช้ต้นฉบับใน bundle
- log: `logs\` ข้าง exe ถ้าเขียนไม่ได้ใช้ `%LOCALAPPDATA%\AETHER\logs\`

### D32 · exe แบบไม่มี console (windowed)
spec ไม่ได้ระบุ — เลือก windowed เพราะเป็นแอป tray/HUD หน้าต่าง console ดำๆ จะเกะกะ ผลที่ตามมา:
- log ทั้งหมดไปที่ไฟล์ และติดตั้ง `sys.excepthook`/`threading.excepthook` ให้ exception ที่หลุดมือลง log
- ข้อความที่ต้องให้ผู้ใช้เห็นตอนเริ่ม (config ผิด, ไม่พบโมเดล, ผล `--check`) แสดงเป็นกล่องข้อความเมื่อไม่มี console
- `python tools/build_exe.py --console` สำหรับ build ไว้ debug

### D33 · การ collect ของ PyInstaller
- mediapipe 1.x ไม่มี hook ใน pyinstaller-hooks-contrib และโหลด `libmediapipe.{dll,so}` จาก package
  `mediapipe.tasks.c` ด้วย ctypes → spec ใช้ `collect_dynamic_libs("mediapipe")` + hidden import
  `mediapipe.tasks.c` + `collect_data_files("mediapipe")`
- mediapipe import `matplotlib` (ใน `drawing_utils`) จึงตัดออกไม่ได้ (~ไม่กี่สิบ MB) และ matplotlib log เรื่อง
  font cache ที่ระดับ INFO จึงตั้ง logger ของ matplotlib เป็น WARNING
- backend ของ pynput ถูก import แบบ dynamic → ใส่ hidden import ของ backend ตาม platform
- ตัด tkinter, Qt WebEngine/Quick/Qml/Pdf/3D/Charts/Sql/Test/Bluetooth, pytest, soundfile
- ไอคอนของ exe (`build\aether.ico`) วาดจากโค้ดเดียวกับไอคอน tray ตอน build — ไม่มีไฟล์รูปใน repo
- **ยืนยันแล้วบน Linux:** build ผ่าน (~30 วินาที, ~620 MB) และ binary ที่ได้รันนอก source tree ได้:
  `--check` โหลดโมเดลผ่าน libmediapipe ใน bundle, เจอฟอนต์ใน `_internal`, เปิดแอปแบบ offscreen แล้ว
  เขียน `logs/aether.log` ข้าง binary และปิดได้เรียบร้อย
- **ยังไม่ได้ยืนยันบน Windows** (เครื่อง dev เป็น Linux): ชื่อ `libmediapipe.dll`, plugin ของ QtMultimedia,
  backend win32 ของ pynput และการรันบนเครื่องที่ไม่มี Python — อยู่ใน checklist M4 ของ README

### D34 · `--check`
เพิ่ม CLI option ที่ไม่มีใน spec: ตรวจ config, โหลดโมเดลแล้วประมวลผลเฟรมว่างหนึ่งเฟรม, ตรวจฟอนต์/เสียง/
calibration แล้วออก (exit 0 = พร้อม, 2 = ใช้ไม่ได้) ไม่ต้องใช้กล้อง — ใช้ตรวจ build หรือการติดตั้งได้ทันที
